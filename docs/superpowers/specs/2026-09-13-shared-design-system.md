# NovaQ Shared Design System Specification\n\n**Status:** Approved shared-system definition\n**Date:** 2026-09-13\n**Scope:** Mandatory design-system contract before page-by-page visual refinement\n**Implementation status:** Definition complete; production implementation not started by this document\n**Canonical system:** `design-system/novaq/MASTER.md`\n\n## 1. Purpose\n\nNovaQ will formally adopt one repository-backed design system before any page-by-page visual refinement. The system consolidates the current React/CSS/Plotly/i18next implementation; it does not replace the frontend stack, introduce unsupported product behavior, or reinterpret analytical evidence.\n\nEvery later UI implementation step must read `design-system/novaq/MASTER.md` first. A page-specific override may exist only when repository evidence and the approved refinement specification justify a real exception.\n\n## 2. Authority reviewed\n\nThis definition is based on:\n\n- `AGENTS.md`, `memory.md`, and `handoff.md`;\n- the approved product decisions, governance, full refinement specification, and implementation plan dated 2026-09-13;\n- `frontend/package.json`, `frontend/src/router.tsx`, `frontend/src/styles/theme.css`, and `frontend/src/styles/global.css`;\n- the current AppLayout, Sidebar, ThemeToggle, LanguageSelector, AnalysisWorkspace, WorkflowNavigator, ApiState, MetricCard, chart, insight, simulation, comparison, and Decision components;\n- `frontend/src/api/types.ts` and `frontend/src/api/workflow.ts`; and\n- `backend/api/workflow.py` and `tests/test_workflow_api.py` for workflow prerequisites and evidence semantics.\n\nThe local UI/UX design-system search returned a minimal/Swiss, navy/grey, dense-dashboard, low-motion direction. Those high-level characteristics fit NovaQ. Its proposed Fira fonts, replacement blue palette, marketing “Enterprise Gateway” pattern, and GSAP animation are not adopted because the repository already has an Inter/system stack, a NovaQ navy/gold identity, an application shell, and no GSAP dependency.\n\n## 3. Compare workflow |\n\n## 4. Adoption decision\n\nNovaQ adopts the current technology and brand foundation:\n\n- React 19 and React Router remain the UI/navigation stack.\n- Global CSS variables in `theme.css` remain the token source.\n- Existing CSS remains the styling system; no Tailwind, shadcn, CSS-in-JS, or new component library is introduced.\n- Plotly remains the chart engine.\n- i18next remains the localization engine.\n- The current Inter/system font stack and navy/gold identity remain.\n- Existing shared components are refined or extracted from repeated current patterns. A new abstraction is allowed only when it has at least two current consumers or fulfills an approved cross-cutting requirement.\n\nThe canonical token names, component contracts, evidence rules, responsive behavior, and accessibility requirements are defined in `design-system/novaq/MASTER.md`.\n\n## 5. Workflow-order conflict\n\nThe requested design direction names:\n\nSetup → Current → Optimize → Simulate → Compare → Decision → Reports.\n\nThat order conflicts with current repository behavior:\n\n- Sidebar and WorkflowNavigator currently use Compare before Simulate.\n- `ComparisonPage.tsx:104-110` persists the scenario selection used by simulation.\n- `SimulationPage.tsx:131-143` directs users to Compare when no scenario is selected.\n- `backend/api/workflow.py:326-350` rejects simulation without that selection.\n- `tests/test_workflow_api.py:167-177` explicitly protects this prerequisite.\n\nTherefore this design-system phase does not silently reorder Simulate before Compare. Its canonical executable order remains:\n\nSetup → Current → Optimize → Compare → Simulate → Decision → Reports.\n\nChanging that order requires a separate workflow specification that relocates or redesigns verified scenario selection and updates navigation, explanatory copy, tests, and runtime behavior without weakening provenance. Until then, responsive navigation must follow the executable repository order.\n\n## 6. Affected implementation surface\n\nLater implementation may refine:\n\n- `frontend/src/styles/theme.css` and `global.css`;\n- AppLayout, Sidebar, ThemeToggle, LanguageSelector, AnalysisWorkspace, and WorkflowNavigator;\n- ApiState, MetricCard, current badges/alerts, and repeated form/table wrappers;\n- ChartFrame and Plotly theme mapping while retaining Plotly and source data;\n- evidence banners derived from current analysis, dataset, scenario, workflow, validation, and Decision records; and\n- frontend tests and both locale files.\n\nThis definition makes no application-code change.\n\n## 7. Protected boundary\n\nThe design system must not change:\n\n- queueing formulas, centralized model selection, model assumptions, stability, or units;\n- optimizer objective, constraints, cost composition, tie-breaking, or payloads;\n- analysis, optimization, simulation, workflow, scenario, auth, or report API contracts;\n- DES/Monte Carlo execution, randomness, trace, aggregate, playback, or validation semantics;\n- scenario provenance, workflow evidence ownership/freshness, or Decision derivation;\n- authentication, authorization, sessions, CSRF, or user scoping;\n- report calculations, Decision gating, export sections, or wait-time conversion to minutes; or\n- the meaning of missing, unsupported, stale, current, optimized, passed, failed, or verified data.\n\n## 8. Completion criteria\n\nThis definition phase is complete when:\n\n1. `design-system/novaq/MASTER.md` defines light/dark semantic tokens, typography, spacing, geometry, motion, and compatibility aliases.\n2. One responsive global-navigation and one workflow-navigation pattern are defined with no duplicated workflow route list.\n3. Shared contracts exist for buttons, fields with units, tables, charts, API states, badges, evidence banners, metrics, tabs, and workflow navigation.\n4. Evidence and workflow status vocabulary is mapped to real repository state and explicitly prohibits visit-based completion.\n5. Chart rules permit only authoritative source measures and require nonvisual alternatives.\n6. Accessibility rules cover focus, keyboard, names, live status/errors, contrast, touch targets, reduced motion, route focus, tables, charts, and language.\n7. The requested workflow-order conflict is documented instead of guessed around.\n8. The approved full-refinement plan names the Master as mandatory input for every UI step.\n\nMeeting these criteria approves later implementation; it does not claim that the current frontend already conforms.\n
