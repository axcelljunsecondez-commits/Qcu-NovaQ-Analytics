Use the review controls to switch line type and page state; the app's own controls (plan switch, Key results / Replay, Advanced) also work. Numbered markers match the notes on the right. Numbers are blank on purpose; chart shapes are placeholders, not results.

1Page header

One h1. Help link opens the "Reading the simulation" guide. The analysis selector opens the last-used analysis.

2Plan switch and page links

Current | Suggested plan picks the run. Key results · Replay · Checks and decision are three separate pages (real routes: /simulation/results, /simulation/replay, /simulation/checks), so each page stays short. Key results opens first. All three use the same run. Suggested needs a selected plan; without one it is disabled with "Choose a plan in Suggested plans first."

P1Key results page

All the key results: Day summary (Current vs Suggested), four charts that show the difference, by period, and by counter for separate lines.

P2Replay page

The moving simulation only: counts, clock, floor, counter states, timeline, controls, event list. "Open full screen" gives the replay the whole window.

P3Checks and decision page

Check different possibilities, then the Decision, then Download report.

3Run bar (one row)

One row: operating hours, closing rule with Change, status, the "Preview · what does this mean?" chip (opens a short explanation), Run full operation, and Advanced. The run label sits on one line below it. Operating hours from setup; "At closing time" is the rule saved for this analysis. The engine badge says which simulation runs: one shared line uses the continuous run (Preview until the version with your recorded service times exists); separate lines use the existing continuous day run.

4Messages by state

Closing rule not set: choose first, nothing preselected. Not supported: names the setting (customers leaving, waiting-space limit), nothing runs. Out of date: old results stay visible, labelled. Running: polite status, result saved even if the user leaves.

5Run label (on all three pages)

"One continuous run · closing rule used · seed · which plan". The run bar is on every page, so a manager can run from wherever they are. One start runs the configured operating hours as one continuous run. Customers keep their identity, place in line, waiting time and unfinished service across period changes. Status: Not run / Running / Done with date / Out of date.

6Advanced settings

Hidden by default. Seed (blank = new each run) and the replay detail limit (value decided in the B4a spec). Defaults are labelled as defaults. Saved results always show the settings they used.

7Headline cards

Four cards, Current → Suggested: average wait, longest line, customers served, not served at closing. The other four rows are under More results. All eight come from the run's totals: mean_wait_hours, waited_count/service_starts, max_queue, time_average_queue, service_starts/arrivals, unserved_customer_count, last_server_release_hours + overrun_hours, busy_server_hours/present_server_hours. Hours shown as minutes. No percentages computed in the browser.

8Two charts up front

People waiting through the day and average wait by period are shown first; arriving vs starting service and counters open vs busy are under More results. From the same run. People waiting is counted from the replay's own events only when the replay is complete; if the replay was cut short, the chart uses the per-period average line length instead and says so. Scheduled breaks are a separate band. Current and Suggested differ by colour and solid vs dashed line, never red vs green. Every chart has a table version.

9More results (closed by default)

The other four summary rows, two charts, the by-period table and (separate lines) the by-counter table. By period: One row per period (1–24), from the run's per-period results (segments[]): arrivals, service starts, average wait, longest line, counters scheduled, busy share. "After closing" shows only what the engine reports for after closing: services started, completions, counter hours (closing.*).

10By counter (separate lines)

From the continuous day run per counter: served, average wait, busy share, longest line. Not a performance score.

MSmooth customer movement

Speeds 0.25×, 0.5×, 1×, 2×, 5×, 10×. 1× = 1 simulated minute per real second (a 13-hour day plays in about 13 minutes; 10× in about 78 seconds). Each customer dot glides between arriving, its place in line, its counter and finished (transform only, eased). Glide time stays between about 0.2 and 0.9 seconds at every speed, so dots never teleport or streak. The line closes up smoothly. Counts and clock always come from the events at that moment; the glide is only how the dot travels there. Paused when the browser tab is hidden. Reduced motion: dots jump without gliding.

11Counter states

Only from simulation events. Separate lines: draining_start → Finishing customers before break (starts 3 minutes before the scheduled break), break_start → On break, break_end → Available. Closed / not staffed from the plan. Never inferred from an idle counter or fewer open counters. Standard shared line has no break states until break modeling is added.

12Replay controls

Restart, Play/Pause, Next event, speed 0.25×–10×, Go to time. Timeline shows period boundaries and scheduled breaks on their own row. Counts satisfy arrived = waiting + being served + finished at every moment. Reduced motion: no dot animation; counts and clock still update.

13Checks (one line each)

Each check is one line: name, status, required or optional, and "details" that opens its numbers, chart and settings. Separate lines: Replay of the day → Many variations → Results check, all required; the Results check refuses to run without saved variations for the latest replay (workflow.py:2800-2810) and the busy limit defaults to the plan's target (workflow.py:146-149). Standard shared line (legacy run): the Results check runs its own simulation and variations (simulation.py:1354-1374), so a separate Many variations run is optional there. Separate lines (exists today): "Many variations" recalculates each period 2,000 times (arrivals ±20%, service ±10%); a variation fails when counters are busy over 75%; holds up when at most 5% fail; range is a 95% interval. "Results check" runs simulation + variations on the plan. One shared line (continuous): repeats the whole day with new random customers and shows ranges only, because no pass/fail rule is approved for this simulation.

14Decision first

The page opens with "Should we use this plan?". Outcomes come only from the saved decision: Yes, go ahead (one shared line, passed and costs the same or less) · Passed but costs more (one shared line) · Passed but saving can't be calculated (separate lines; their best outcome) · Change the plan first (with failed periods) · Not enough checks yet (with what is missing) · Out of date. Before any check: "No decision yet" and Check the plan, which runs Many variations, then the Results check, then asks the server for the decision (three existing requests for separate lines). After: the plain outcome from the saved decision, Download report, Check again. One shared line (continuous): not available until a pass/fail rule is approved. That is a new owner decision.

15Run details

Engine version, seed, run time, closing rule and settings, so any run can be repeated exactly.
