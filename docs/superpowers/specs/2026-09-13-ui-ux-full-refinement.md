# NovaQ Full UI/UX Refinement Specification\n\n**Status:** Approved refinement specification\n**Date:** 2026-09-13\n**Scope:** Repository-grounded trust repair, workflow refinement, visual consistency, responsive behavior, accessibility, localization, and report-preview fidelity\n**Implementation status:** Not started by this specification\n\n## 1. Authority and precedence\n\nThis specification follows the repository authority order in `AGENTS.md`: current source and tests, `memory.md`, `handoff.md`, relevant documents under `docs/`, and then older session material.\n\nThe following current documents were reviewed:\n\n- `AGENTS.md`, `memory.md`, and `handoff.md`;\n- `docs/superpowers/specs/2026-09-13-ui-ux-refinement-product-decisions.md`;\n- `docs/superpowers/specs/2026-09-13-ui-ux-refinement-governance.md`;\n- `docs/superpowers/specs/2026-09-13-shared-design-system.md` and `design-system/novaq/MASTER.md`;\n- the current workflow-integration design, plan, verification report, and restructure audit;\n- the current analysis-workspace, optimization-save, authentication, simulation-playback, and interface-review specifications; and\n- the current frontend, backend, report generator, and regression tests cited below.\n\nThe current repository supersedes stale findings. In particular, the older findings “DES equivalence not proven” and “Decision evidence missing” are excluded from refinement scope. Current `simulate_segments_with_trace()` returns aggregate results and bounded playback events from one execution (`backend/queueing_engine/simulation/simulation.py:679-700`), with equivalence and trace-cap regression coverage in `tests/test_simulation.py:172-222`. Workflow evidence is persisted and Decision freshness is derived from that evidence in `backend/api/workflow.py:150-234,493-522`, with persistence, deterministic Decision, and staleness coverage in `tests/test_workflow_api.py:127-305`. This implementation is protected.\n\n## 2. Approved outcome\n\nNovaQ will become a truthful, coherent, accessible, responsive, bilingual operations-analytics workflow without changing validated analytical or security semantics. Trust-repair items are implemented first; systemwide visual refinement follows only after those items pass focused tests.\n\nThe intended workflow is:\n\nLogin → required first-use onboarding → analysis setup → upload data → Current → Optimize → save/select scenario → Compare → Simulate/Validate → Decision → Reports.\n\nReturning users who completed onboarding enter normally. Help provides a voluntary onboarding replay. Page copy distinguishes observed input, analytical/model output, optimization candidates, simulation evidence, Decision state, and projections.\n\n## 3. Explicit product/repository conflict\n\nThe approved product intent is separate FIFO cashier queues, while priority-class queueing is outside the capstone scope. The current repository does not implement that intent end to end:\n\n- `backend/api/analysis_schemas.py:63-64` classifies `separate_queues` as `unsupported`;\n- `frontend/src/pages/AnalysisSetupPage.tsx:41-42` exposes the value but warns that it is unsupported; and\n- current DES/playback explicitly reports `queue_structure: "shared"` at `backend/queueing_engine/simulation/simulation.py:670`.\n\nThis refinement must not resolve the conflict by relabeling shared FIFO as separate FIFO, by silently mapping separate/priority choices to shared FIFO, or by changing queueing mathematics. Until a separate analytical feature specification defines models, request/response behavior, DES behavior, validation, evidence, reports, and tests for separate queues, the UI must state that separate cashier queues are the intended product mode but are unavailable in this repository version. Priority routing must not appear as supported.\n\nImplementing separate-queue mathematics is outside this specification.\n\n## 4. Verified defects and intended behavior\n\n### P0-01 — Broken entry links and false login claims\n\n- **Verified problem:** Dashboard quick actions navigate to routes that do not exist, and Login describes the working authentication flow as an unconnected mockup while also depicting unsupported queue behavior.\n- **Evidence:** `frontend/src/pages/DashboardPage.tsx:12-14` links to `/optimize`, `/simulate`, and `/compare`; actual workflow routes are analysis-scoped in `frontend/src/router.tsx:78-103`. `frontend/src/pages/DashboardPage.test.tsx:74-75` currently locks the invalid links. `frontend/src/pages/LoginPage.tsx:69,150` says “INDIVIDUAL QUEUES” and claims authentication is not connected.\n- **Current behavior:** Quick actions fall through the router, and the login page contradicts the production-backed auth implementation and current shared-FIFO limitation.\n- **Intended behavior:** Dashboard actions either start/select an analysis before entering its real scoped route or use a valid analysis-scoped route. Login accurately describes NovaQ and does not promise unsupported queue structure or mock authentication.\n- **Affected surface:** `DashboardPage.tsx`, `DashboardPage.test.tsx`, `LoginPage.tsx`, router-aware navigation helpers, and both locale files.\n\n### P0-02 — Onboarding is not in the authenticated first-use flow\n\n- **Verified problem:** Onboarding is public, optional, saves placeholders, and states the wrong workflow order.\n- **Evidence:** `frontend/src/router.tsx:74-78` places `/onboarding` outside `RequireAuth`. Both actions in `frontend/src/pages/OnboardingPage.tsx:35-45` persist `operation_type: "other"` and an empty terminology object; lines 109-114 show “CURRENT → OPTIMIZE → SIMULATE → COMPARE” and “Skip for now.” The backend already persists actual fields at `backend/api/onboarding.py:19-25,48-54`.\n- **Current behavior:** First-time users are not reliably gated; “continue” and “skip” are equivalent placeholder writes; returning and replay behavior are undefined.\n- **Intended behavior:** Add an authenticated onboarding guard using the existing status API. Incomplete first-time users are routed through onboarding once; completed users are not forced again. Remove skip, collect real operation type and terminology preferences, preserve an intended destination, and add an authenticated Help route/action that replays onboarding voluntarily without clearing completion.\n- **Affected surface:** `router.tsx`, a new onboarding guard, `OnboardingPage.tsx`, auth navigation tests, a small authenticated Help page/entry, API client types already serving onboarding, Sidebar, and both locales.\n\n### P0-03 — Guided setup silently changes intent and duplicates canonical setup\n\n- **Verified problem:** The Guided Setup presents priority/automatic routing but serializes it as shared queue, converts unanswered capacity/abandonment questions to definite assumptions, and collects an operation type that is never included in its setup payload.\n- **Evidence:** `frontend/src/pages/GuidedSetupPage.tsx:45-46` maps the “Priority or automatically assigned” choice to `shared_queue`; lines 64,85-87 map unused or null state into concrete values. Its option cards are custom clickable containers instead of native grouped form controls. The canonical form already exists at `frontend/src/pages/AnalysisSetupPage.tsx:41-48`, including an unsupported separate-queue warning; its patience-rate input permits zero while the backend requires a positive value.\n- **Current behavior:** Two setup paths can produce different or invented meanings.\n- **Intended behavior:** Merge plain-language guidance into the canonical Setup and make `/guided-setup` a compatibility redirect to `/setup`. Preserve unknown values until the user decides, remove priority as a supported choice, retain the separate-queue limitation disclosure, use native labeled controls, and align client validation with the existing positive backend constraint.\n- **Affected surface:** `GuidedSetupPage.tsx` and its CSS/imports, `AnalysisSetupPage.tsx`, `router.tsx`, analysis setup types/client validation, tests, and locales.\n\n### P0-04 — Current-state conclusions are not always data-derived\n\n- **Verified problem:** Current shows unconditional operational conclusions, miscounts critical intervals, truncates arrival display without disclosure, and can misrepresent more than three selected models.\n- **Evidence:** `frontend/src/pages/AnalysisCurrentPage.tsx:128,237` asserts high/concentrated pressure without a data condition. Line 142 searches uppercase `CRITICAL` while `backend/queueing_engine/services/data_processing.py:48-56` emits `Critical`. Lines 166 and 186 silently slice to 13 values. Lines 73-78 compute any number of model categories while the visual treatment only provides a fixed small palette. Structured model explanations already come from `backend/queueing_engine/services/model_explanations.py:48-96`.\n- **Current behavior:** The page can state a problem that the rows do not show, report zero critical intervals incorrectly, omit periods silently, or collapse model categories visually.\n- **Intended behavior:** Normalize status counting, derive every conclusion from current rows/KPIs, show neutral “no critical intervals” or unavailable states when appropriate, use the backend explanation fields, and display all periods/categories or explicitly expose the visible range and a complete table.\n- **Affected surface:** `AnalysisCurrentPage.tsx`, shared chart/table components, page tests, and locales.\n\n### P0-05 — Optimize copy misstates the objective and candidate status\n\n- **Verified problem:** A preset is described as “Minimize Wait Time … even if it costs more,” output is labeled “Ideal,” and an explicitly entered available cashier pool of zero avoids the shortage verdict.\n- **Evidence:** `frontend/src/pages/OptimizePage.tsx:31-48` only changes `target_utilization` and `max_wait_minutes`; `frontend/public/locales/en/translation.json:239-242` describes distinct objectives. The optimizer always minimizes total configured cost among feasible candidates and uses constraints at `backend/queueing_engine/services/optimization.py:187-342`. `OptimizePage.tsx:257` only computes a pool gap when the pool is greater than zero; line 268 says “Ideal Staffing Plan.”\n- **Current behavior:** Presentation implies a mathematical objective that does not exist, overstates an unvalidated result, and hides a real zero-capacity gap.\n- **Intended behavior:** Rename presets to cost-focused, low-wait, and balanced constraint profiles; show the exact utilization/wait constraints each applies; label output candidate/model-recommended until validation and Decision; describe available pool as a post-hoc coverage comparison that is not sent as an optimizer constraint; and handle zero as a provided value.\n- **Affected surface:** `OptimizePage.tsx`, its tests, and both locales. Backend optimizer and payload remain unchanged.\n\n### P0-06 — Comparison invents scores and unsupported projections\n\n- **Verified problem:** Comparison generates arbitrary frontend-only 0–100 radar scores, labels cost scaling as ROI without investment cost or an explicit base-period contract, divides by zero, and treats missing metrics as zero.\n- **Evidence:** `frontend/src/lib/radar.ts:47` creates the score; `frontend/src/pages/ComparisonPage.tsx:285-287` renders it through `frontend/src/components/charts/Charts.tsx:245`. `frontend/src/pages/ComparisonPage.tsx:112,281-326` calls the ROI helper and displays daily/monthly/annual savings; `frontend/src/lib/roi.ts:22-24` applies calendar scaling. No persisted `operating_period`, `base_period`, or `investment_cost` contract exists in the searched repository. `frontend/src/pages/ComparisonPage.tsx:204,207-209` has a zero denominator and substitutes zero for missing values.\n- **Current behavior:** Synthetic, untraceable scores and unsupported ROI/projections can appear alongside real model results.\n- **Intended behavior:** Remove the radar score/chart and ROI/projection block. Keep direct, unit-labelled current-versus-candidate measures and modeled cost difference for the analyzed period. Render unavailable values honestly, average only finite present values, and guard percentage calculations. Monthly/annual projection controls remain deferred until base-period/scaling metadata exists; ROI remains prohibited until investment cost exists.\n- **Affected surface:** `ComparisonPage.tsx`, `radar.ts`, `roi.ts`, their tests/imports, chart exports, and both locales.\n\n### P0-07 — Simulation validation display can use the wrong threshold\n\n- **Verified problem:** After a persisted validation run, changing the editable failure-cap field can recompute the displayed pass/fail verdict without rerunning, while Decision uses the persisted run parameter.\n- **Evidence:** `frontend/src/pages/SimulationPage.tsx:81,108-119,154-155,298-331` stores the live form value and uses it for display. Evidence exposes persisted `params` in `frontend/src/api/workflow.ts:8,84-101`. Backend Decision reads `validation.params.mc_failure_rate_cap` at `backend/api/workflow.py:493-522`.\n- **Current behavior:** Simulation and Decision can appear to disagree even though Decision correctly uses persisted evidence.\n- **Intended behavior:** Display validation verdicts using the persisted evidence threshold. Editing run settings affects only the next run; when current inputs differ from persisted parameters, show “settings changed—rerun to replace evidence.” Complete tab semantics and avoid continuously announcing playback clock updates.\n- **Affected surface:** `SimulationPage.tsx`, evidence helpers/types if needed, simulation page tests, Live playback accessibility only, and locales. DES execution, evidence persistence, and Decision logic remain unchanged.\n\n### P0-08 — Report preview promises sections absent from exports\n\n- **Verified problem:** The UI promises ten sections, including simulation validation, ROI, and appendix content, while current PDF/Excel generators produce fewer, format-specific sections.\n- **Evidence:** `frontend/src/pages/ReportsPage.tsx:2,26-36,141` and `frontend/public/locales/en/translation.json:154-173` advertise ten sections. PDF creates Executive Summary, Segment Comparison, and Recommendations after its title page at `backend/reports/report_export.py:259-383`. Excel creates Summary, Segments, and Recommendations only when applicable at lines 427-561.\n- **Current behavior:** Preview and generated artifact do not match.\n- **Intended behavior:** Make preview format-specific and exact: PDF shows title, Executive Summary, Segment Comparison, and Recommendations; Excel shows Summary, Segments, and conditional Recommendations. Remove claims for absent simulation, ROI, methodology, or appendix sections. Preserve current generators and Decision-gated report source.\n- **Affected surface:** `ReportsPage.tsx`, report page tests, and both locales. Export generation and API contracts are unchanged.\n\n### P1-01 — Shared accessibility and responsive defects\n\n- **Verified problem:** Core typography is undersized, focus is suppressed for controls, the shell does not establish a valid narrow-screen layout, and shared states/tables/charts lack complete semantics.\n- **Evidence:** `frontend/src/styles/global.css:16,65-94` uses 14 px body, 11 px table text, 9 px headers, and `outline: none`. Numerous 9–11 px rules remain; `.app-shell` starts at line 25 but the 900 px rules at lines 975 and 1140 do not make the full shell a reliable single-column mobile layout. Only a narrow playback animation rule exists at line 2184. `frontend/src/components/layout/AppLayout.tsx:8` has no skip link/target; shared `frontend/src/components/ui/ApiState.tsx` lacks consistent live status/alert semantics.\n- **Current behavior:** Keyboard focus, readability, mobile layout, status announcements, and nonvisual data access are inconsistent.\n- **Intended behavior:** Add a visible skip link and main target; global `:focus-visible`; WCAG AA contrast; 16 px default body and at least 14 px functional table/form text; 44 px touch targets on compact widths; no page-level horizontal scroll at 375/768/1024/1440; complete loading/error/empty/stale semantics; semantic table captions/headers; chart summaries and accessible data alternatives; and global reduced-motion behavior.\n- **Affected surface:** `global.css`, `AppLayout.tsx`, shared UI/chart components, page tables, responsive Sidebar, and tests.\n\n### P1-02 — Theme, language, icon, and localization consistency\n\n- **Verified problem:** Theme state can become stale, document language is not synchronized, structural navigation uses text glyphs, and major workflow pages still contain hard-coded English and inline colors.\n- **Evidence:** `frontend/src/components/layout/ThemeToggle.tsx` derives mode from the DOM without React state; `frontend/src/lib/i18n.ts:22` changes i18next but does not update the document `lang`; `frontend/src/components/layout/Sidebar.tsx:29-49` uses text glyphs as structural icons; Current, Optimize, Guided Setup, and other inspected pages contain hard-coded copy/colors. Design and interaction requirements\n\n- Every page refinement must follow `design-system/novaq/MASTER.md`; any page override requires repository evidence and separate approval.\n- Preserve the recognizable NovaQ navy/gold identity. Use a restrained, high-contrast, information-dense operations dashboard; do not add a new external font or decorative visual dependency.\n- Consolidate primitive and semantic color, spacing, radius, elevation, type, status, and focus tokens in `global.css`. Replace affected inline hard-coded colors with tokens.\n- Gold may remain an accent but must not carry white text where contrast fails. Text and status meaning must not rely on color alone.\n- Desktop controls may remain compact at a minimum 36 px height; at narrow/touch layouts interactive targets must be at least 44×44 px.\n- Use one main page heading, logical heading order, persistent analysis/scenario context, and a single canonical next/back navigation area.\n- All controls require programmatic labels, keyboard operation, visible non-obscured focus, disabled explanation where needed, and explicit async/loading/error/success states.\n- Tables require captions or accessible names and proper header scope. Dense tables may scroll inside a labelled region, but the page itself must not horizontally scroll.\n- Charts must retain source values and units, include a concise text summary and table/list alternative, avoid color-only distinctions, and expose complete categories/ranges.\n- Respect `prefers-reduced-motion`; motion is optional decoration, not state communication.\n- Every affected string must use i18n and exist in English and Filipino with key symmetry.\n\n## 7. Acceptance criteria\n\n1. Every dashboard workflow action resolves to a real route/state; Login contains no mock-auth or unsupported-queue claim.\n2. A logged-in incomplete user is sent to onboarding once; completion stores selected real preferences; a completed user is not forced again; Help can replay it.\n3. Canonical Setup is the only editable setup flow. The legacy guided URL redirects. Unknowns remain unknown; priority is absent; separate queues are visibly unavailable pending the separate feature spec.\n4. Current page critical counts and narrative match fixtures for zero, some, all, missing, and mixed-case statuses. Charts disclose or show all data/categories.\n5. Optimize presets are described as constraint profiles; their numeric settings are visible; output remains a candidate until evidence/Decision; available pool zero produces the correct comparison.\n6. Comparison contains no synthetic score, ROI, monthly, or annual claim. Direct values retain units; zero/missing/non-finite data produces no NaN, Infinity, or false zero.\n7. Validation display uses the persisted run threshold. Edited settings are identified as pending rerun; backend Decision remains unchanged.\n8. PDF and Excel previews exactly list their current generated sections, including conditional Excel Recommendations, and advertise no absent content.\n9. Keyboard-only users can reach navigation, controls, tabs, dialogs, tables, and replay; focus is visible and not obscured; the skip link reaches main.\n10. Normal text meets 4.5:1 contrast, large/non-text UI meets 3:1, document language follows the selected locale, and reduced motion is respected.\n11. At 375, 768, 1024, and 1440 px there is no page-level horizontal scroll, clipped primary action, or inaccessible navigation; data tables use contained labelled overflow when necessary.\n12. English and Filipino render all changed flows with symmetric keys and no raw translation keys.\n13. Protected regression suites remain green and source/API snapshots show no protected semantic changes.\n\n## 11.
