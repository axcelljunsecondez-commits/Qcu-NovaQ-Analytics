# NovaQ workflow integration design

Date: 2026-09-13

## Outcome

NovaQ's active-analysis workflow is:

`Setup -> Current -> Optimize -> Compare -> Simulate -> Decision -> Reports`

The sidebar is the only major-stage navigation. Each page also has a contextual
bottom Back/Next control whose label names the destination. Setup's internal
progress indicator remains local to Setup and is not a second major navigation.

## Allowed changes

- Frontend routing, navigation, page composition, translations, and tests.
- Additive authenticated workflow endpoints.
- Reuse of the existing `jobs` table for immutable workflow evidence. Its
  documented purpose already includes simulations and batch work.
- DES process instrumentation so aggregate metrics and playback events are
  emitted by the same SimPy execution.
- Analysis-scoped report recommendation input.

## Protected boundaries

- Queueing formulas, centralized model selection, optimizer equations and
  constraints, Monte Carlo distributions/confidence rules, scenario snapshot
  verification, ownership checks, and existing response fields are unchanged.
- Existing `/simulation/des`, `/simulation/des/trace`, `/simulation/mc`, and
  `/simulation/validate` routes remain compatible. No endpoint is deleted.
- Dataset and Scenario records remain immutable in meaning. Workflow evidence
  refers to their IDs rather than copying or rewriting their source records.

## Persistent evidence model

No schema migration is required. Completed evidence is stored as user-owned
`Job` records with an `analysis_id`, `scenario_id`, and `dataset_id` in
`params_json`. Latest means greatest job ID for the matching user, analysis,
scenario, and kind.

Kinds:

- `workflow_selection`: selected verified Scenario from Compare.
- `workflow_des`: unified DES aggregate results plus the bounded event trace.
- `workflow_mc`: standalone Monte Carlo evidence.
- `workflow_validation`: combined DES/Monte Carlo validation evidence.
- `workflow_decision`: deterministic recommendation and its evidence IDs.

Changing the selected scenario does not mutate earlier records. Evidence for a
previous selection remains auditable but is not treated as current.

## Unified DES

One internal customer/arrival lifecycle drives both aggregate monitoring and
optional event recording. Event recording consumes no random draws. The legacy
aggregate endpoint invokes the lifecycle without a recorder. The trace endpoint
invokes it with a bounded recorder and returns additive `results` generated by
that exact execution. Reaching the event cap stops recording, not simulation,
so aggregate results still cover the requested horizon.

The frontend exposes one `DES & Live Playback` category. Its playback, KPI
cards, tables, charts, and CSV use the single trace response. The old aggregate
playback UI and separate Live tab are removed; the API compatibility endpoint
is retained.

## Scenario input

Compare may select only a user-owned Scenario in the active Analysis with a
server-verified calculation snapshot and operationally complete optimized rows.
Simulation input is derived server-side from those immutable rows:
`lambda_ -> lambda`, `mu -> mu`, `c_optimal -> c`, plus supported variance,
capacity, and patience fields. Browser-supplied queue rows are not accepted by
workflow persistence endpoints.

## Deterministic Decision derivation

Decision is never free-form or generated. It is derived only from persisted
facts for the current selected Scenario.

Required evidence:

1. completed Setup;
2. a valid analysis-scoped Dataset;
3. a selected verified, operationally complete Scenario;
4. a completed unified DES run with no unsupported/error row;
5. a completed validation run whose DES and Monte Carlo evidence is available.

If any item is absent, status is `insufficient_evidence`; recommendation text
lists the missing evidence and makes no adoption claim.

For complete evidence, each validation row passes only when simulation is
supported, no validation reason exists, DES status is not Error/Critical/
Unstable, the Monte Carlo failure rate is at or below its persisted cap, and
the failure-rate confidence interval is adequate. If any row fails, status is
`revise`; the recommendation is not to adopt the selected Scenario yet. If all
rows pass, status is `adopt` when modeled optimized cost does not exceed current
cost, otherwise `conditional`. The saved rationale includes scenario identity,
modeled cost delta, server delta, validation counts, and the analytical-versus-
simulated provenance warning. These rules do not change optimization outputs.

## Reports

When `analysis_id` is supplied, report generation looks up the current persisted
Decision. Its recommendation and rationale replace independently generated
recommendation text. If no matching Decision exists, the report states that a
management recommendation is unavailable because Decision evidence is
incomplete. Legacy report calls without `analysis_id` retain existing behavior.

## Completion criteria

- Numeric active-analysis sidebar paths in the required order; no `/latest`.
- Duplicate horizontal major-stage navigation removed.
- Bottom Back/Next labels identify the adjacent stage.
- Compare selection survives refresh.
- All Simulation categories use the persisted selected Scenario.
- DES playback and charts come from one backend execution.
- Persisted evidence is ownership-scoped and stale Scenario evidence is ignored.
- Decision derivation is covered by pass, fail, and insufficient tests.
- Analysis-scoped Reports consume the matching Decision.
- Repository backend, lint/type, frontend test/type/lint/build gates pass.
