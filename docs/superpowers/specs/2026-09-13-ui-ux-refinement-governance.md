# NovaQ UI/UX Refinement Governance\n\n**Status:** Approved process baseline\n**Date:** 2026-09-13\n**Scope:** Sequencing and gates for the full NovaQ UI/UX refinement\n\n## Governing rule\n\nNovaQ may improve visual design, usability, accessibility, responsive behavior, explanatory copy, and workflow clarity. Those changes must not silently alter queueing mathematics, model selection, optimization behavior, simulation evidence, Decision rules, security controls, provenance, or report semantics.\n\nThe work must proceed through the following five phases in order.\n\n## Phase 1 — Trust Repair\n\nCorrect misleading or inconsistent P0 behavior before broad visual refinement.\n\nThis phase is limited to defects where the current interface contradicts implemented behavior, saved evidence, route behavior, supported queue behavior, or generated output. Examples identified by the audit include:\n\n- invalid Dashboard workflow links;\n- false authentication and onboarding claims;\n- setup choices that silently change user intent;\n- unconditional or incorrectly counted Current-state conclusions;\n- optimization copy that misstates the objective;\n- synthetic or insufficiently qualified comparison values;\n- validation status calculated with a threshold different from the persisted run; and\n- report previews that do not match generated exports.\n\nPhase 1 must use the smallest regression-safe change that restores truth. It is not authorization for a broad redesign or a new analytical feature.\n\n### Phase 1 exit gate\n\n- Each P0 defect has a repository-grounded reproduction or source trace.\n- The corrected user-facing behavior is explicit.\n- Relevant regression tests exist or are planned.\n- No protected behavior is changed without a separately approved defect specification.\n\n## Phase 2 — Specification\n\nDocument exactly what the full refinement will change before implementing it.\n\nThe specification must identify:\n\n- affected routes, pages, shared components, and states;\n- navigation and workflow behavior;\n- copy and terminology changes;\n- responsive behavior at target widths;\n- accessibility behavior;\n- design tokens and component variants;\n- data provenance, units, assumptions, and missing-value presentation;\n- English and Filipino translation changes;\n- tests and acceptance criteria; and\n- intentionally unchanged behavior.\n\nEvery significant existing page or component must receive one action classification: KEEP, REFINE, MERGE, MOVE, REPLACE, REMOVE, or KEEP PENDING VERIFICATION.\n\n### Phase 2 exit gate\n\n- Scope is complete and reviewable.\n- Product decisions and unresolved questions are explicit.\n- Acceptance criteria are testable.\n- No implementation is hidden inside the specification.\n\n## Phase 3 — Safety Boundary\n\nDeclare the analytical and security behaviors that implementation must not change.\n\nAt minimum, the boundary must cover:\n\n- centralized queue-model selection;\n- queueing formulas, units, stability checks, and model assumptions;\n- optimizer objective, constraints, tie-breaking, and cost composition;\n- scenario snapshots and provenance;\n- DES and Monte Carlo request/response behavior;\n- equivalence of DES aggregate results and playback trace;\n- workflow evidence ownership, persistence, freshness, and Decision staleness;\n- deterministic Decision derivation;\n- authentication, authorization, sessions, CSRF, and tenant/user scoping;\n- report units, Decision gating, and export contracts; and\n- i18n key symmetry.\n\nThe boundary must map each protected behavior to its implementation source and existing or required regression test.\n\n### Phase 3 exit gate\n\n- Protected contracts are enumerated.\n- Every contract has a verification method.\n- Any approved exception is explicit and separately justified.\n\n## Phase 4 — Implementation\n\nRefine the product only within the approved specification and safety boundary.\n\nImplementation must:\n\n- be incremental and traceable to specification items;\n- preserve user data and existing scenario/evidence relationships;\n- avoid unrelated cleanup;\n- update both locales for every new user-facing string;\n- keep analytical terminology plain-language-first without removing technical precision;\n- preserve accessible keyboard and screen-reader behavior; and\n- stop for a new decision if implementation would cross a protected boundary.\n\n## Phase 5 — Verification\n\nVerification must prove both:\n\n1. the P0 defects are gone; and\n2. protected NovaQ behavior remains unchanged.\n\nVerification must include focused regression tests plus the repository gates appropriate to the changed scope:\n\n- `python -m pytest tests/ -x --tb=short`;\n- `ruff check .`;\n- `mypy .`;\n- `npm test`;\n- `npm run typecheck`;\n- `npm run lint`; and\n- `npm run build`.\n\nUI verification must also cover:\n\n- keyboard navigation and visible focus;\n- screen-reader names and status announcements;\n- contrast in light and dark themes;\n- reduced motion;\n- English and Filipino;\n- loading, empty, error, stale, and disabled states;\n- report-preview/export fidelity; and\n- responsive behavior at 375, 768, 1024, and 1440 pixels.\n\n## Change-control rule\n\nWhen a refinement conflicts with a protected behavior, implementation must stop. The team must document the conflict, evidence, proposed change, analytical or security impact, migration needs, and regression coverage before requesting separate approval.\n
